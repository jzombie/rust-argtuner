# Plan: Fix CI failures from the mock-bin pipe-mode refactor

## Problem

Two independent CI failures after the pipe-mode / mock-bin-crate work:

1. **Windows — compile error**: `test_support.rs:30` calls `CommandRunner::force_pipes_for_tests()`,
   but it is `#[cfg(not(windows))]`-gated. On Windows it doesn't exist → `E0599`.
2. **macOS + Ubuntu — runtime panic** in every lib test using a mock bin:
   `CARGO_BIN_EXE_emit_result is unset and target/debug/emit_result does not exist`.
   Root cause (verified empirically): `cargo test --workspace --bins` compiles bin targets as
   **test-harness binaries into `target/debug/deps/`**, never producing `target/debug/<bin>`.
   The regular binaries come only from `cargo build`. CI runs
   `cargo test --workspace --all-features --lib --bins --tests --examples` with no prior build,
   so `target/debug/emit_*` are absent → `bin_path` panics.

## Changes

### 1. `src/command/subprocess/runner.rs` — make the hook exist on Windows

`CommandRunner::force_pipes_for_tests()` must compile on all platforms. On Windows the runner
already always uses pipes (`run_piped`), so the hook is a no-op:

```rust
    /// Test-only: force all subprocesses in this process to use piped stdio
    /// instead of a PTY (avoids the macOS PTY buffer-destruction race on child
    /// exit). Idempotent; safe to call from any test thread. No-op on Windows,
    /// where subprocesses always run over pipes.
    #[cfg(windows)]
    #[doc(hidden)]
    pub fn force_pipes_for_tests() {}

    #[cfg(not(windows))]
    #[doc(hidden)]
    pub fn force_pipes_for_tests() {
        FORCE_PIPES.store(true, Ordering::Relaxed);
    }
```

### 2. `.github/workflows/rust-tests.yml` — build the mock binaries before testing

Insert a step before the `Test` step that builds the workspace bins (producing
`target/debug/emit_*`), so the mock-bin subprocesses resolve via `bin_path`:

```yaml
      - name: Build mock binaries
        run: cargo build --workspace --all-features --bins
```

(Matches the existing `--all-features` matrix flag; cheap on cached runners.)

### 3. `src/test_support.rs` — no change needed

`bin_path` already falls back to `<workspace>/target/debug/<bin>` (with `.exe` on Windows) and
panics with actionable instructions if absent — after the CI build step, the path always
exists. (Optional polish, not required: reword the panic to mention the `cargo build --bins`
command too.)

## Verification

- `cargo build --workspace --all-features --bins` then
  `cargo test --workspace --all-features --lib --bins --tests --examples -- --include-ignored`
  (the exact CI command) — all green, on this machine.
- Cross-check the harness placement: `cargo test --bins` puts bins in `target/debug/deps/`;
  `cargo build --bins` puts them in `target/debug/` — confirmed the CI step is required.
- Windows-specific: `cargo check -p argtuner` under `--target x86_64-pc-windows-msvc` is not
  available here; the `#[cfg(windows)]` no-op is trivial and matches the pre-existing
  `#[cfg(windows)] run` pattern, so compile correctness is assured by structure.
- `cargo clippy --workspace --all-targets --all-features -- -D warnings` and
  `cargo fmt --all -- --check` — clean.

## Notes

- The separate unpublished `argtuner-mock-bin` crate stays (primary goal: mock bins never ship
  in the published `argtuner` package). The tradeoff is that `cargo test` alone needs a prior
  `cargo build --workspace --bins`; the CI workflow now does this explicitly, and the panic
  message documents it for local runs.
