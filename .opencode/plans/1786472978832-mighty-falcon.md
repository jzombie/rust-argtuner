# Plan: Fix intermittent PSO test flake ("result missing key 'metric'") under `--workspace --all-features`

## Problem

`sampler::pso::tests::pso_end_to_end_checkpoint_persisted_and_restored` intermittently
fails under `cargo test --workspace --all-features`:

```
===== Finished Trial 1: ERROR =====
Error: result missing key 'metric'
thread 'sampler::pso::tests::pso_end_to_end_checkpoint_persisted_and_restored' panicked
  at src/sampler/pso.rs:578:29: second PSO run (warm restart): result missing key 'metric'
```

Facts established:
- **Not a rand 0.10 regression.** Passes in isolation (with and without `--all-features`),
  passes the lib suite repeatedly, and a full `--workspace --all-features` run passed.
  Intermittent only under heavy parallel load.
- The harness execs the compiled `emit_result` binary directly (`test_support::bin_command`
  prefers `CARGO_BIN_EXE_*` / `target/debug/<bin>`), so the `cargo run` fallback is not the cause.
- **Root cause (per review):** the mock subprocess binaries emit their `::ARGTUNER::` lines and
  exit immediately. On macOS, closing the PTY slave at process exit can destroy the kernel's
  output buffer before the parent's master-side reader drains it, so the tail line
  (`model.epoch_end` — emitted last by `emit_result`) is permanently lost → empty payload →
  `result missing key 'metric'`. The reader (`spawn_reader`) is correct as-is; `portable-pty`
  already maps child-exit `EIO` to EOF, and polling after EOF is futile.

## Changes

### 1. Mock emit binaries — keep the PTY slave open after flushing (source-level fix)

In each mock subprocess binary under `src/bin/`, at the very end of `main()` (immediately
before process exit), flush stdout and hold the process open so the parent's master reader
can drain the kernel PTY buffer. **Order matters: flush strictly before the sleep**, and the
sleep is **50 ms** (not a tighter value) to survive thread-starvation scheduling jitter in
highly parallel/CI environments:

```rust
// Keep the PTY slave open long enough that the parent's master reader drains
// the buffered ::ARGTUNER:: lines before this process exits (macOS PTY race).
// Flush first, then hold; 50 ms to tolerate scheduling jitter under load.
std::io::Write::flush(&mut std::io::stdout()).ok();
std::thread::sleep(std::time::Duration::from_millis(50));
```

Affected files (all exit right after emitting):
- `src/bin/emit_result.rs`  (the flaking PSO test driver)
- `src/bin/emit_binding_version.rs`
- `src/bin/emit_env_result.rs`
- `src/bin/emit_invalid_result.rs`
- `src/bin/emit_invalid_then_ok.rs`
- `src/bin/emit_result_marker.rs`
- `src/bin/emit_x_used.rs`

No changes to `src/command/subprocess/runner.rs` — `spawn_reader` behavior is untouched
(immediate termination on `Ok(0)`).

### 2. `src/command/objective.rs` — self-explanatory metric error (diagnostic)

Append the subprocess stdout tail to the missing-metric error at `objective.rs:304-306` so any
recurrence exposes the raw stdout state:

```rust
let metric = payload
    .get_metric(&self.metric_key)
    .map_err(|err| EvalError::Other(format!("{err} (stdout tail: {:?})", tail_lines(&output.stdout, 3))))?;
```

- `output` is still in scope (only borrowed by `parse_payload` earlier); `tail_lines` already
  exists at `objective.rs:15`.
- Leading text `result missing key '<key>'` stays unchanged (grep test expectations for that
  string before editing).

## Files modified

- `src/bin/emit_result.rs` + the six other `src/bin/emit_*.rs`
- `src/command/objective.rs`

## Verification

- `cargo build --workspace` (rebuilds the mock bins), then
  `cargo test -p argtuner --lib sampler::pso::tests::pso_end_to_end_checkpoint_persisted_and_restored -- --exact` — passes.
- Stress: loop the PSO test ~5× under `--all-features`, then `cargo test --workspace --all-features` a few times — no failures.
- `cargo clippy --workspace --all-targets --all-features -- -D warnings` and `cargo fmt --all -- --check` — clean.
- Confirm the mock bins still emit identical output: run `./target/debug/emit_result` and
  verify the two `::ARGTUNER::` lines are unchanged (output appears after the ~50 ms hold).
- If the flake ever recurs, the improved error now prints the stdout tail, revealing whether
  the subprocess produced no output (PTY loss — confirms the sleep fix is the right layer)
  or produced output that wasn't parsed (points elsewhere).

## Honest caveat

The race was not reproduced locally, so the sleep is a targeted, low-risk mitigation for the
most plausible cause (macOS fast-exit PTY buffer destruction), with a 50 ms window sized to
outlast thread-scheduling jitter. The diagnostic (item 2) is the safety net: if it still
flakes, the next error message tells us definitively where to look.
