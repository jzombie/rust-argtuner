# Plan: `argtuner inspect` — parse a config toml and show the structs it deserializes into (with a README assertion)

## Problem
The README's template/config example (`template = "cargo run ..."`, abstract `[sampler]`/`[scheduler]` sketches) doesn't convey how the template system actually works with a real config. The user wants:
1. A parsing utility that takes an `argtuner.toml` and displays the struct information argtuner actually deserialized from it.
2. A realistic README example (adapted from a real-world config: multi log-scale floats, `{trial_dir}`, successive-halving budget placeholder).
3. An "assertion in the README itself" — a test proving the README's shown config + inspect output match reality, replacing manual eyeballing/hackish json-reading.

This mirrors the existing pattern in `tests/protocol_schema.rs` (`<!-- marker -->` fenced block + assert-equal test).

## Changes

### 1. `src/project/mod.rs` — add `Project::load_unified_config()`
- `pub fn load_unified_config(&self) -> std::io::Result<UnifiedConfig>` — the existing read-parse mapping (same error style as `load_config`).
- Refactor `load_config`, `read_template`, `read_space` to call it (removes the current triple re-parse of the toml). Behavior unchanged.

### 2. `src/inspect.rs` (new lib module)
`pub fn render_inspect(project: &Project) -> std::io::Result<String>` producing a deterministic, path-only-labeled dump:
```
project: examples/config_showcase

[project]
metric_key = "val_loss"
...                ← normalized TOML round-trip of the parsed UnifiedConfig
[space]
[[space.params]]
type = "Float"
...

template:
  <the template verbatim, indented 2 spaces>

placeholders:
  {noise}:     space param Float in [0.01, 0.5], log-scale
  {steps}:     space param Int in [20, 300], step 20; scheduler budget placeholder (overridden per rung)
  {trial_dir}: reserved: per-trial artifact directory (auto-injected)
  {trial_id}:  reserved: numeric trial id (auto-injected)
```
- Parse via `project.load_unified_config()`.
- Normalized config TOML: `toml::Value::try_from(&config)` → `toml::Table`, remove the `template` key, `toml::to_string_pretty`. (Confirms exact API at compile time; fallback `toml::Table::try_from(&config)`.) This round-trip shows what argtuner actually parsed, including applied defaults and normalized field names (e.g. input `log = true` → `log_scale = true`).
  - **No derive changes needed**: every type in the round-trip already derives `Serialize` — `UnifiedConfig`, `ProjectSettings`, `SamplerConfig`/`RandomSamplerConfig`/`PsoSamplerConfig`, `SchedulerConfig`/`FixedSchedulerConfig`/`SuccessiveHalvingSchedulerConfig`, `Goal`/`Sampler`/`Pruner` (src/project/config.rs), `SearchSpace` and `ParamSpec` (src/search_space/mod.rs). `Project::save_unified_config` already round-trips `UnifiedConfig` via `toml::to_string_pretty`. (`ProjectConfig` is NOT part of the round-trip — it is a flattened view with no `Serialize` derive and stays out of scope.)
- Placeholder analysis from `CommandTemplate::placeholders()` (BTreeSet → sorted, deterministic). Each token annotated against `ParamSpec` by name; `trial_id`/`trial_dir` annotated as reserved (via `constants::PLACEHOLDER_TRIAL_ID/DIR`), respecting `inject_trial_placeholders`; successive-halving budget note when `scheduler.kind == Scheduler::SuccessiveHalving` and token == `budget_placeholder`.
- The `project:` label uses `project.root()` rendered with **forward-slash normalization**: `root.to_string_lossy().replace('\\', "/")`. This keeps the asserted output byte-identical on Windows CI (where `PathBuf` uses `\`) so the README block (Unix separators) matches there too. No other CWD-dependent content.

- Dispatch arm: `crate::inspect::render_inspect(&Project::new(path))`, print on success, `eprintln!("Error: …")` + exit 1 on failure (matching existing arms).
- `cli_tests`: add `inspect_requires_project` parse test (no arg fails, with dir parses).

### 4. `src/lib.rs` — `pub mod inspect;`

### 5. `examples/config_showcase/` (new committed project)
- `argtuner.toml` — realistic config translated from the user's real-world one into current format, runnable against the existing `loss_pattern_generator` example (accepts `--steps`, `--noise`, `--metric-key`, `--checkpoint-dir`, `--epoch-time`):
  - Template: `cargo run -p argtuner --example loss_pattern_generator -- --pattern noisy --steps {steps} --noise {noise} --metric-key val_loss --checkpoint-dir {trial_dir} --epoch-time 1` (guitar_tuning-style `'''` indented literal).
  - `[project]`: metric_key "val_loss", goal "min", `inject_trial_placeholders = true`.
  - `[sampler]`: type "random".
  - `[scheduler]`: type "successive_halving", n_trials 30, seed 42; `[scheduler.successive_halving]`: budget_placeholder "steps", min_epochs 20, max_epochs 300, eta 3.
  - `[space]`: `noise` Float `log = true` [0.01, 0.5]; `steps` Int [20, 300] step 20.
- `README.md` — brief: what it demonstrates, `argtuner run examples/config_showcase`, `argtuner inspect examples/config_showcase`.
- No `main.rs` → not a cargo example target, so `cargo test --examples` (CI) is unaffected.
