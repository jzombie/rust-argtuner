## Future proposals (NOT in the immediate scope — standalone designs)
These are substantial architectural epics; each gets its own proposal before
implementation.

### Future A — Conditional hyperparameters
- **Gap:** `ParamSpec`/`ParamHint` are flat; no conditional dependencies
  (e.g. `learning_rate` only when `optimizer == "sgdt"`).
- **Remediation (future):** extend `ParamSpec`/`ParamHint` with `parent` +
  `parent_values`; conditional sampling/validation/template-rendering; `inspect`
  shows the dependency. Own proposal defines the AST/serde shapes.

### Future B — Process-tree hygiene & trial timeouts
- **Gap (verified):** runner has no process-group management (`setpgid`/`killpg`
  / Job Objects) and no per-trial timeout; cancelling/interrupting a trial can
  orphan sub-child workers (PyTorch, multi-GPU).
- **Remediation (future):** per-trial process groups + group kill on
  abort/timeout; config-driven per-trial timeout. Own proposal covers the
  platform-specific signal handling.

### Future C — Multi-objective optimization
- **Gap:** scoring is a single scalar (`metric_key`).
- **Note:** **no DB schema migration is needed** — `trial_records` stores a
  generic `fields_json` map, so arbitrary `metric.*` fields already persist. The
  gap is purely scoring/sampler-level: the protocol scores one key, and samplers
  track one best. A future MOO proposal would extend the sampler/scheduler
  traits for multi-objective evaluation and Pareto-front tracking (e.g. NSGA-II),
  leaving storage unchanged.
