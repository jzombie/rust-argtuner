# Production-readiness gaps for PSO checkpoint resume + stale-Running sweep

## 1. End-to-end sweep + resume integration test (HIGH)

**Problem:** Unit tests verify `sweep_stale_running_trials` in isolation and PSO checkpoint resume in isolation, but nothing tests the full chain:

1. Run PSO (creates trials, saves checkpoint)
2. Simulate Ctrl-C (leaves a trial `Running` with artifact dir)
3. Call tuner resume (which calls `sweep_stale_running_trials` then `run_pso`)
4. Verify checkpoint was loaded, stale trial was swept, PSO continued

**Files:** `src/sampler/pso.rs`, `src/checkpoint.rs`

**Implementation:**
- Add test to `src/sampler/pso.rs` that:
  - Creates project with PSO config + `emit_result` binary
  - Runs PSO for a few iterations
  - Injects a stale `Running` trial into the store (bypassing the objective)
  - Creates an artifact dir for that stale trial
  - Calls `sweep_stale_running_trials` then `run_pso` again
  - Verifies: stale dir deleted, stale trial is `Error`, PSO resumed at correct iter

## 2. User notification of swept trials (MEDIUM)

**Problem:** `sweep_stale_running_trials` runs silently. If a user resumes and finds trials changed to `Error` with artifacts deleted, they have no way to know why.

**Files:** `src/checkpoint.rs`, `tuner/mod.rs`

**Implementation:**
- Make `sweep_stale_running_trials` log each swept trial ID with `eprintln!`
- In `tuner/mod.rs`, after the sweep, print a summary line:
  `eprintln!("INFO: cleaned up {n} stale trial(s) from previous run");`
- (Optional) Consider a dedicated notification channel later, but stderr is sufficient for now

## 3. Search space bounds validation on checkpoint load (MEDIUM)

**Problem:** If the user changes search space bounds (min/max) between runs, the checkpoint's unit [0,1] positions map to different actual HP values than originally intended. The solver clamps positions so it won't crash, but the resumed run explores a different space.

**Files:** `src/sampler/pso.rs`, `src/search_space/mod.rs`

**Implementation:**
- Store the search space (at minimum param names and bounds) alongside the checkpoint in `project_metadata`
- On checkpoint load, compare saved space against current config
- If bounds differ, warn the user and either:
  - Reject the checkpoint (start fresh)
  - Or accept it with a warning (user may have intentionally shrunk bounds)

## 4. SHA promoted trials lose training progress after sweep (LOW)

**Problem:** When a stale `Running` parent is swept and its artifact dir is deleted, the promoted SHA child that would have copied its checkpoint starts from scratch instead. This is safe (the `parent_dir.exists()` guard skips the copy) but silent — the user loses training progress.

**Status:** Already tested by `parent_artifacts_skipped_when_parent_dir_missing`.

**Remaining work:** The sweep summary message (item 2) is sufficient notification. No code change needed here beyond item 2.

## 5. Cache misses for swept Error trials with no score (LOW)

**Problem:** After sweep, stale trials become `Error` with no `FIELD_SCORE`. `build_trial_result_cache` correctly excludes them (no score → skip). But when PSO revisits that HP config, it's a cache miss and the command runs from scratch instead of returning a cached result.

**Assessment:** This is correct and desirable — the command was never completed, so there's nothing to cache. No code change needed.

## 6. CSV-only edge case (LOW)

**Problem:** If a user manually edits `trials.csv` without keeping the SQLite DB in sync, the sweep (which reads from DB) would miss stale entries entered only in the CSV.

**Assessment:** This is an unsupported edge case. The DB is the source of truth; CSV is a cache/snapshot. No code change needed.
