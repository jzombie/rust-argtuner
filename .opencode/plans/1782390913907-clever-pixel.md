# Plan: Add Per-Step Event Data with In-Memory Caching

## Problem

Users who want per-step metrics call `emit_epoch_end()` on every training step → immediate
SQLite write + full CSV rewrite per step. Bad for SSD lifetime.

## Solution

New `StepEnd` event type. Steps are **cached in memory** during an epoch and **flushed to
DB at epoch end**. For real-time TUI visibility, the tuner pushes step updates via **TCP
localhost IPC** (cross-platform, no OS-specific code).

Step data is **DB-only** (no CSV). New `trial_step_records` SQLite table.

## Design

### Data flow

```
Trial binary stdout (::ARGTUNER:: JSON lines)
  → parse_payload() collects step_results: Vec<BTreeMap>
  → objective caches steps in-memory per trial
  → when emit_epoch_end() fires:
      1. Flush cached steps to trial_step_records in DB
      2. Write epoch record (existing behavior)
      3. Push step data to TUI via TCP (real-time)
  → TUI: listens on TCP for live steps + reads past steps from DB
```

### IPC mechanism

- **TCP on localhost** (127.0.0.1) — works on Linux, macOS, Windows with zero OS-specific code
- **Well-known port range** (e.g., 45100–45110):
  - Tuner tries each port in order, binds the first free one, prints to stderr
  - TUI scans the range trying to connect; first successful connection wins
  - No files, no CLI flags required
- Simple JSON push: `{"trial_id": 1, "steps": [{fields}, ...]}`
- Fire-and-forget, no ACK needed
- Falls back gracefully if no TUI is connected

## Files to modify

### 1. `crates/common/src/lib.rs` — New event kind

- Add `StepEnd` variant to `EventKind`
- Add `STEP_END_EVENT = "step_end"`, `MODEL_STEP_END_EVENT = "model.step_end"` constants
- Handle in `from_name()`, `as_str()`

### 2. `bindings/rust/src/lib.rs` — New binding API

- Add `pub fn emit_step_end<T: Serialize>(value: &T)`
- Add `Talkback::emit_step_end(&self, value)` convenience method

### 3. `src/command/subprocess/runner.rs` — Collect step results

- Add `step_results: Vec<BTreeMap<String, String>>` to `CommandResultPayload`
- In `parse_payload()`, when `EventKind::StepEnd`, collect fields into `step_results`
- Add `step_fields()` method

### 4. `src/trial/db.rs` — New table + CRUD

- Add `trial_step_records` table (same schema as `trial_epoch_records`)
- Add `insert_step_record()`, `load_step_records()`, `reset_trial_steps()`
- Schema in `execute_batch`

### 5. `src/trial/store.rs` — Step cache + flush + IPC publisher

- Add `step_cache: Arc<Mutex<HashMap<usize, Vec<TrialRecord>>>>`
- Add `cache_step(trial_id, record)`, `flush_steps(trial_id)`, `load_step_rows()`
- Add TCP publisher thread that accepts TUI connections and pushes step updates

### 6. `src/command/objective.rs` — Hook into epoch lifecycle

- Accept step results alongside epoch results from payload
- After epoch processing (line 350-358): cache + flush steps, push to TUI
- At trial success/error: any remaining cached steps are flushed

### 7. `src/tui/mod.rs` — Read step data + TCP subscriber

- Add `step_rows: BTreeMap<i64, Vec<TrialRow>>` to `AppState`
- Spawn TCP subscriber thread that connects to tuner and receives step updates
- In `refresh_trials()`, load steps from DB + merge with live socket data
- Step data uses existing X-axis logic (`metric.step`)

### 8. `src/tuner/mod.rs` — Step publisher lifecycle

- Start TCP publisher before sampling loop
- Pass publisher handle to `TrialStore`
- Shutdown after run completes

### 9. Example binaries — Update

- `crates/tooling/loss-pattern-generator`/`examples/linear_regression.rs`:
  `emit_step_end()` per iteration, `emit_epoch_end()` at epoch boundaries

## Cross-platform note

TCP on localhost works on all platforms. If any platform-specific optimization is added
(e.g., Unix sockets on Linux/macOS), the fallback to TCP must be preserved and the
platform-specific path annotated with a `// TODO: <platform> support` comment.

## Tests

### Unit tests (`cargo test`)

1. **`crates/common`**: Test `StepEnd` serializes to `model.step_end`, round-trips through `from_name()`
2. **`bindings/rust`**: Test `emit_step_end()` produces correct JSON on stdout
3. **`src/command/subprocess/runner.rs`**: Test `parse_payload()` collects step events into `step_results`, separate from `epoch_results`
4. **`src/trial/db.rs`**: Test `insert_step_record()` + `load_step_records()` round-trip, verify schema creation
5. **`src/trial/store.rs`**: 
   - Test `cache_step()` + `flush_steps()` — steps cached in memory, appear in DB only after flush
   - Test `load_step_rows()` returns flushed steps
   - Test `sync_csv()` does NOT include step data (verify CSV output unchanged when only steps exist)
6. **`src/command/objective.rs`**: Test that steps are flushed at epoch end (when `append_epoch()` is called), not at each step arrival
7. **TCP IPC**: Test publisher-subscriber with an in-memory mock TCP stream — verify JSON messages sent/received

### Integration tests

8. **End-to-end with `emit_*` binaries**: Write a test binary that emits 10 steps then 1 epoch end, run it through the subprocess runner, verify:
   - 10 step records in `trial_step_records`
   - 1 epoch record in `trial_epoch_records`
   - 1 trial record (from the final result)
   - CSV contains only the trial + epoch records (0 step rows)
9. **Resume test**: Steps from a prior run survive a cache rebuild (`load_step_records()` after restart)
10. **Edge case**: Trial ends with error — cached steps are still flushed before error update

### Manual verification

- `argtuner run` + `argtuner watch` simultaneously:
  - Step data visible in TUI during an epoch (before flush)
  - Step data persists after epoch end
  - No per-step writes to DB or CSV
  - No temp files created
